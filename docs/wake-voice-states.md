# 唤醒词与常驻语音: 三个概念与正确的顺序

这份文档要解决一件事: **设置页那个开关现在等于"常开麦克风"**, 而它该等于的只是"允许用唤醒词"。
记录现状 (错在哪、错在哪一行)、该有的状态机、以及改完怎么判它对了。

> **2026-10-06 的现状注记 (读下面之前先读这一段)**: 这份文档记的是 2026-10-05 那次改动的决策过程,
> 它描述的**三层结构还成立** (许可 / 唤醒词监听 / 识别那一路, 顺序仍然是"门卫命中才轮到它"), 但
> **常驻语音的入口变了**: 那一次的结论是"两个许可" (「允许唤醒」+「允许常驻语音」, 后者默认关),
> 而主人在 2026-10-06 实测之后判定**后一个许可多余** —— 它在手机模式下也能把识别链打开, 于是对话
> 一直进行下去。所以:
>
> - 设置页那个「允许常驻语音」开关与浮标菜单那行「一直听」**都删了**
> - 识别那一路现在只由三条路打开: 唤醒词命中 / 球上点一下 (**用完就收**, 闲置 10 s), 以及**视频
>   模式** (它是唯一要求这一路留着的; 切进视频模式时由 `LwModes` → `LwWakeWord.resident` 打开,
>   退回收回, 记号是 `modes/voice-resident.on`, 设备端脚本 `modes/video.sh` 走同一份实现)
> - **2026-10-07 又多了一个"现在别听"的开关**: 设置页的「省电模式」+「省电时段」(见
>   `docs/wake-word.md` 第六节)。它停的**只是唤醒词那一条** (麦克风整个关掉, 喊不醒), host /
>   浮标 / 通知都留着, 点球那一下仍会把麦克风临时借来说一句 —— 所以它既不是"收回许可", 也不是
>   当年那个「一直听」
>
> 下面正文里凡是说"两个许可"或"设置页那个开关"的地方, 都按这一段读 —— 那两层结构没变, 变的是
> 谁有资格打开第二层。

## 一、三个概念, 现在被压成了两个

| 概念 | 该由谁表达 | 触发条件 | 生命周期 | 代价 |
| :-- | :-- | :-- | :-- | :-- |
| **允许唤醒** (设置项) | 一个存盘的偏好 | 人在设置页拨一下 | 跨重启, 一直有效 | 不该有任何运行时副作用 |
| **唤醒词监听** | `WakeWordState.listening` + `KeywordSpotter` | 允许唤醒 + 模型与词表齐 + 麦克风权限 | 跟进程走, 命中不退出 | 一份 16 kHz 采集 + 3.3M 参数的 KWS |
| **常驻语音** (常开麦克风那一半) | `VoiceState.capturing` + `SpeechSegmenter` + `SenseVoice` | **唤醒词命中**, 或用户当场明说 | 命中打开, 闲置超时关 | 240 MB 识别器 + VAD + 持续 CPU 与耗电 |

**正确顺序是 2 → 3**: 唤醒词是低功耗的门卫, 只有它命中之后才轮到常驻语音。设置项是 2 的前置许可,
不是 3 的开关。现在的实现把这三件事全焊在一个布尔上, 所以打开设置项 = 直接进入第 3 态。

## 二、错在哪: 常驻语音不是被谁打开的, 是被"起服务"顺带带出来的

这不是"某个 `if` 写反了"那一类 bug, 是**常驻语音从来没有过一次独立的决定** ——
`WakeWordService.startListening()` 里那三块是按顺序无条件铺开的:

```
 1. KeywordSpotter(...)          →  唤醒词          (该有的)
 2. prepareSegmentation()        →  silero VAD      ← 无条件
 3. prepareRecognition()         →  SenseVoice      ← 无条件 (240 MB 到第一段才真加载)
 4. AudioCapture(...).add(halfDuplex) + start()
 5. VoiceState.capturing = true  →  对外宣称"常驻语音在跑"  ← 无条件
```

第 2 与第 3 步的注释自己写着它们是"尽力而为的附加链", 可是**附加链没有自己的开关** ——
它们跟着服务起来, 而服务是被设置页那个开关起来的。于是:

- 设置页拨一下 → 常驻语音也开了, 不管人想不想要
- 通知栏的文字里直接印着 `常驻识别在跑` (真相: 人在设置页只是想"允许喊一声")
- 输入框上沿那个麦克风胶囊也出来, 而它对应的语义是"持续吃麦克风"

### 具体耦合点

| # | 位置 | 现在是什么 | 为什么是错的 |
| :-- | :-- | :-- | :-- |
| 1 | `wake/WakeWordService.kt` `startListening()` (223-224 行 `prepareSegmentation()` / `prepareRecognition()`) | 起服务就把 VAD 与识别链一起铺开 | 常驻语音在这里被"顺带"打开, 没有第二个人问过 |
| 2 | `WakeWordService.kt` 226 行 `device.add(halfDuplex)` + `halfDuplex` (254-258 行) | 一个采集循环喂 KWS 与 VAD 两个消费者 | 采集循环本身没有"只喂 KWS"这一档; 只有一个既成事实的合体 |
| 3 | `WakeWordService.kt` 241 行 `VoiceState.capturing = true` | 与 `WakeWordState.listening = true` (235 行) 成对写 | 两个概念共用一个生命周期, 状态机因此只有一个维度, 表达不出"KWS 在听而常驻关着" |
| 4 | `tool/LwWakeWord.kt` `listen()` (312-319 行) | 递归调 `start()`, 起的就是整条服务 | 设置页那个开关的唯一落点; 它与通道那条 `op=start` 是同一个实现 (注释里还把这个当成优点) |
| 5 | `ui/SettingsScreen.kt` `WakeItems()` (929-949 行) | `SwitchPreference(checked = WakeWordState.listening, onCheckedChange = { LwWakeWord.listen/hush })` | 开关直接等于监听, 而监听又直接等于常驻语音 —— 两层等于串成一条 |
| 6 | `wake/WakeWordService.kt` `listeningText()` (515-525 行) | 最后那个分支无条件说 `常驻识别在跑` | 界面在替人宣称一件他没要求过的事 |
| 7 | 下载那一条 (951-999 行) 与改词那一条 (1013-1037 行) | 下完模型 / 存完词表就 `listen()` | 同一个错的第二、第三个入口: 为了"能用"把常驻链也一起开 |
| 8 | `channel/LwModes.kt` (172-177 行) | 进视频模式就 `lw_wakeword op=start` 起整条链 | 换了个触发口, 但落点仍是"整条链", 所以是同一个错误的复用 |

**出口症状的准确位置**是 3 + 6 + 5 三处叠出来的: `WakeWordState.listening == true` 与
`VoiceState.capturing == true` 同时为真, 通知栏写着"常驻识别在跑", 而用户本意只是"允许喊一声"。

### 权限模型那一侧, 还有一个更细的问题

`LwWakeWord` 里 MICROPHONE 那个 `Capability` 的 `why` 写的是"唤醒词要一直听着麦克风"
(`tool/LwWakeWord.kt` 50-54 行) —— 措辞没错, 但**"允许唤醒"至今没有一个自己的偏好键**。
唯一的持久状态是 `WakeWordState.listening`, 那是个跟进程走的运行时量。所以现在**没法表达"允许唤醒
但此刻没在听"**, 设置页只能拿运行时状态去画那个开关。要修语义, 先得有那个键。

## 三、该有的状态机

```
        ┌──────────────────────────────────────────────────────────┐
        │  偏好: 允许唤醒 (存盘) + 允许常驻语音 (存盘, 默认关)        │
        └──────────────────────────────────────────────────────────┘
                     │ 前置许可, 本身不起任何服务
                     ▼
  ┌─────────┐   ① 许可齐 + 模型与词表齐 + 麦克风权限在    ┌──────────────────┐
  │  OFF    │ ───────────────────────────────────────▶ │  KWS 守着唤醒词    │
  │ 没在听   │ ◀─────────────────────────────────────── │  麦克风开着, ASR 关 │
  └─────────┘              ⑤ 收回许可                    └──────────────────┘
                                                                  │
                                            ② 命中唤醒词           │
                                     (或用户当场明说)              ▼
                                                          ┌──────────────────┐
                                                          │  常驻语音 + KWS    │
                                                          │  VAD 切段 + 出字   │
                                                          └──────────────────┘
                                                                  │
                                            ③ 闲置超时 (N 秒没活动) │
                                                                  ▼
                                                            回到 KWS 态
```

三条转换的意义各自要说清:

- **① 是"允许唤醒"唯一的作用**: 它只决定 KWS 起不起。它**不碰** VAD, 不碰 SenseVoice, 不碰
  `VoiceState.capturing`
- **② 是"常驻语音"唯一的开门条件**: 命中之后才建切段器与识别器。于是 240 MB 的识别器在命中之前
  不进内存, 通知栏也不再宣称"常驻识别在跑"。**这一次开门永远发生**, 与"允许常驻语音"那个许可无关
  —— 那个许可决定的是这一路**留不留着** (`sticky`), 不是"能不能听到一句话"
- **③ 是省电的那一半**, 也是最容易被漏掉的一半: 没有它, 一次命中就等于"常驻语音一直挂着" ——
  那是把设置开关那个错换了个位置再犯一次。超时值 **10 s** (`VOICE_IDLE_MS`; 主人 2026-10-05 先定
  20 s, 真机上看过之后改成 10 s, 因为这一段就是"说完最后一句之后它还在吃麦克风"的时间)。
  **`sticky` 为真时不收**: 那是"允许常驻语音"开着的态, 主人要的就是一直听 —— 所以这一条只管唤醒词
  命中的那一次

  **③ 有一条例外是 2026-10-09 补的** (主人: "语音输入没说完自动退出"): 助手**正在想**
  (`OverlayState.phase` = 宿主写进 `ball-phase.json` 那一笔账) 或**正在念** (`VoiceState.speaking`)
  的时候, 这一笔闲置账**挂起** —— 那两个状态正是主人最可能在"想下一句怎么说"的时候, 窗口自己收了,
  下一句就得重新喊唤醒词。两个都退掉之后账从那一刻重新起算, 所以仍然有完整的一份 10 s
  (`VoiceIdle.held`, 判据在 `VoiceIdleTest`)

  **但这一档只管"还没说到一句"的那一段** (2026-10-09 同一天的第二条: 主人"说完后发送问题, 正在听
  状态没有结束, 应该结束掉才对" + "要看还在不在说"): 一句话出字**投出去之后**上限换成
  `WakeTuning.SENT_TAIL_MS` (0.3 s) 而且**不再挂起** —— 人声照样算活动 (还在说就继续听, 不会被从
  中间收掉), 一停下来 0.3-0.8 s 就收 (看门狗节拍 500 ms)。于是"一次唤醒 = 一句话", 而问完等回答的
  那几十秒里窗口不会一直挂着。代价: 一句话中间停顿超过 0.8 s 被 VAD 切成两段时, 后半句要重新喊一次

### 半双工: 定了走 A (TTS 期间连 KWS 一起闭嘴)

现在 `VoiceState.speaking` 一为真, `halfDuplex` 让 KWS 与切段一起闭嘴 (`WakeWordService.kt` 254-258
行), 理由是"不采就不会把自己的声音录回去"。**主人 2026-10-05 定: 保留 A** —— 接受"念回答那几秒
叫不醒"这个盲区, 换掉自唤醒的风险。

> **2026-10-09 真机上补的那一条 (在线引擎念的时候闸没合上)**: 那道闸的判据原来是
> `VoiceState.speaking`, 而**只有系统引擎与自带引擎会写它** —— 在线那两条 (Edge / API) 一个字节都没
> 写。于是用在线引擎念回答时麦克风照开着: 喇叭里念的那句被录回去、又当成"主人说的一句话"投进会话
> (主人的原话: "把她自己的说录入听里去了"; 日志里那一条 `segment queued as #24: 主人素云在主上若无
> 别的事…` 就是她的回答正文), 而球上同时显示成**「正在听」**而不是「正在念」。两处都修了:
> `LwSpeak.speak()` 现在把**三条引擎整段**包在 `VoiceState.speaking = true` 里, 而判据改成
> `VoiceState.speaking || LwSpeak.speakingNow` (闸与球都用这一个并集) —— 以后再加引擎时, 少写一处
> 标记也关得住

A 是对的时候, 状态机里要多表达一件事: **半双工是一道单独的闸, 不是"ASR 关掉"**。它要满足两条:

- KWS 与 ASR **一起**闭嘴, 不能只关 ASR (那就是 B 了)
- TTS 结束后 ASR 从**干净的一段**重新开始: 闸合上时不能只是丢样本, 因为 VAD 手里还留着 TTS 之前
  那半句没切完的话音, 它会在几秒之后被混进新音频里, 切成一段拼起来的话。所以要在闸合上时让切段器
  把手里的**作废** (`abandon()` → `Vad.reset()`, 已于 2026-10-05 实装), 下次开门就是新的一段。
  **不是 `flush()`**: `flush()` 是"把剩下的交出去", 那等于把半句话送进会话, 还会把"唤醒之后的头一句"
  这个位置占掉 —— 交出去比丢掉糟

念回答时那段"叫不醒"的窗口要**在通知栏如实说** (与"静音 0.8 秒"那条纪律同一个道理: 静音是一个
状态, 不是一个看不见的副作用)。

### 唤醒词命中: 开一个新对话, 转写投进去

**主人 2026-10-05 定**: 命中唤醒词就开一个新对话, 随后那句话在新对话里跑。

**2026-10-06 改口径, 这一节的目标那半作废**: 主人要的是"只要是 1 小时内, 无论点球/喊唤醒词 都只在
同一场对话" (**2026-10-07 那个数由主人改成 20 分钟, 2026-10-11 又缩到 10 分钟**) —— 头句不再另开一场, 选场只看
`voice/session.json` 那一笔账, `wake` 只剩"这是头一句"
的记号 (见 `docs/floating-input.md`)。下面这一段保留作当时的记录。

这一条落在投递那一半 (宿主侧), 不在采集那一半。现在 `voiceTargetSession`
(`host-plugin/index.mjs` 3429-3439 行) 的规矩是 **正在跑的轮优先 → 否则最近动过的根会话**,
也就是说现在这句话会**插进主人正开着的那一轮**, 而不是开新对话。改成"唤醒词命中就新开一个"要动两处:

1. **应用侧标记**: `VoiceInbox` 那条记录多一个字段 (`wake: true`), 只有**命中之后的头一句**带它。
   一个"唤醒窗口" = 命中到命中之后的第一句话出字, 这一句之后的都回到老规矩 —— 否则一句话被 VAD
   切成两段时会开出两个对话
2. **宿主侧读取**: `voiceDeliver` 见到这个标记就**跳过 `voiceTargetSession` 直接 `controller.create({})`**,
   也就是不再 steer、不再选最近那个 (即使此刻有别的轮在跑)

**这件事有一个必须知道的后果**: Web GUI 那边**不会自己切过去**。会话是 `sessionController.create`
建的, 而界面看哪一个是浏览器自己的路由状态, app 这一侧没有一条"让页面切会话"的路
(`HostScreen.kt` 里 `evaluateJavascript` 只用于自检与那个麦克风胶囊)。所以新对话真的在跑、回答也
真的会念出来, 但**人可能正看着另一个会话**。两条路, 都需要拍板:

| 走法 | 后果 |
| :-- | :-- |
| **只开新对话, 不切界面 (主人 2026-10-05 选定, 改动最小)** | 说一句话, 回答念出来了, 但界面上看不见那一轮 |
| 连界面一起切过去 (已否) | 要另找一条"让 dsh 的 Web GUI 跳到一个会话"的路 (GUI 自己的路由, 不是公开 API), 成本与风险都高一档 |

## 四、设置页那个开关的语义修正

### 现在的两行

```
标题: 一直听着                     (settings_wake_listen)
摘要: 开着时麦克风一直开着, 通知栏留一个「停止」; 命中会震一下…  (settings_wake_listen_summary)
状态: 没在听; 打开下面那个开关就开始   (settings_wake_state_idle)
```

这三句说的都是"麦克风一直开着", 也就是**常驻语音**的语义。所以现在这个开关当着用户的面把
"允许唤醒"说成了"常开麦克风" —— 与代码里的耦合是一回事, 只是先在人话里发生。

### 改法: 拆成"许可"与"状态"两件事

**设置页只放许可, 不放开关**:

| 行 | 新语义 | 文案方向 (示意) |
| :-- | :-- | :-- |
| 状态文字 | 如实说 KWS 在不在听、常驻语音在不在跑、各缺什么 | 「正在听「肥鱼肥鱼」」/「没在听; 打开下面那个开关就开始」 |
| 下载唤醒词模型 | 不变, 但下完**不自动** `listen()` | 「模型已就绪: 4 个文件, 逐个对过 sha256」 |
| 唤醒词 | 不变 (改词之后 KWS 重启是必要的) | 不变 |
| **允许唤醒** | 新的开关, 落一个新偏好键 (`wake-allow`, 缺省**开**) | 「允许唤醒: 允许这个应用听唤醒词」 |
| **允许常驻语音** | 第二个开关, 缺省**关** (`wake-allow-voice`) | 「开着时麦克风在命中之后一直留着…关着时每次喊一声仍然能讲一句话, 说完就收回去」 |

关键在最后两行**分开**, 而且**分工要说准**: 前一个管"听不听唤醒词", 后一个管"那一句之后**留不留着**"。
一次唤醒**永远**能听到一句话 —— 那个许可不是"能不能听到", 是"留不留着"。写成"关着就连命中都不开"
会让这个功能自相矛盾: 喊醒了却听不见你说什么 (这一版的第一稿就是这么写的, 走查 diff 时抓到并改掉)。

### 文案要一起改的四处

1. `settings_wake_listen` / `settings_wake_listen_summary` (两份 strings.xml 都要, 键与顺序对齐)
2. `settings_wake_state_idle` 里"打开下面那个开关就开始"这句要跟着新语义走
3. `WakeWordService.listeningText()` 那个 `常驻识别在跑` 分支 (只在 ASR 真跑时才说)
4. `wake_badge_listening` (输入框那个胶囊的文案) —— 它对应的是"持续吃麦克风", 所以**只在 ASR
   真的在跑时才出现**, 不该在纯 KWS 态就跳出来

### 通知栏那条常驻怎么分

现在只报"正在听「X」", 改完要能看出两条链各自的状态。建议一句话里两段:

```
正在听「肥鱼肥鱼」                    ← 纯 KWS 态, 隐私指示只该对应这一半
正在听「肥鱼肥鱼」· 常驻语音在跑       ← ASR 也开着
```

`「停止」`那个按钮仍然是**一下就关掉全部** (它关的是服务, 与现在一致), 这与
"一直开着的麦克风必须有一眼看得见、一下就关得掉"那条纪律不冲突 —— 那条纪律约束的是**可见性**,
不是要求两个开关各配一个按钮。

## 五、落地顺序 (按耦合点 1-8)

**九步全部实装 (2026-10-05)**, 每一步的判据与它落在哪儿:

| 步 | 改什么 | 判据 | 落在哪 |
| :-- | :-- | :-- | :-- |
| 1 | `WakeWordState` 添 `voiceAllowed` / `voiceActive`, `VoiceState.capturing` 只在 ASR 真跑时置真 | 起服务后 `capturing` 仍是 false | `WakeWordService` / `VoiceState` |
| 2 | `startListening()` 拆开: KWS 与采集先起 (只 `add(halfDuplex)`), `prepareSegmentation` / `prepareRecognition` 挪进 `openVoice()` | 起服务后 `vadReady` 仍是 false, 日志里没有 VAD 与 SenseVoice 那两行 | `startListening()` / `openVoice()` |
| 3 | `hit()` 调 `openVoice()` (受"允许常驻语音"管) + 置"唤醒窗口"标记 + 闲置 10 s 自动收回 (`closeVoice` / 看门狗) | `hits` 从 0 变 1 的那一刻日志里才出现切段器与识别器; 静 10 s 后回到纯 KWS | `hit()` / `openVoice()` / `closeVoice()` / `startWatchdog()` |
| 4 | 两个新偏好键 (`wake-allow` 缺省开 / `wake-allow-voice` 缺省关) + 设置页拆两个开关 | 拨开关只写偏好, `capturing` 不动 | `LwWakeWord.allow/setAllow` + `SettingsScreen` |
| 5 | `listen()` / 下载 / 改词三处的"顺手开常驻"拿掉 | 下完模型只起 KWS | `LwWakeWord.listen` / `SettingsScreen` |
| 6 | 通知栏与胶囊文案按两条链分别说 | 纯 KWS 态下通知栏不出现"常驻"字样; 胶囊不出现 | `listeningText()` / `WakeBridge` / `WAKE_BADGE_JS` |
| 7 | `LwModes` 视频模式改成"只给常驻语音那个许可 + 起 KWS", 手机模式只收回那个许可 | 进视频模式后 `capturing` 仍是 false (只在命中后才真) | `LwModes.set` |
| 8 | 半双工 (A): 闸合上时 `abandon()` (作废, 不是 `flush()`), 且通知栏说"正在念回答, 先不听" | TTS 前后那两句话不会被切成一段拼起来的话 | `SpeechSegmenter.abandon()` / `halfDuplex` / `startSpeakingWatch()` |
| 9 | `VoiceInbox` 记录加 `wake` 字段 (只有唤醒之后的头一句带) + `voiceDeliver` 认它开新对话 | 命中后那一句落在一个**新建**的会话里, 而不是插进正在跑的那一轮 | `VoiceInbox.append` / `deliver()` / `voiceDeliver` |

**还补了几处开关与状态之间的缝** (写码与走查时才发现, 不补就会留下"改了不生效"或"拿别人的决定
去做他没要求的事"):

- **许可改了要告诉正在跑的服务**: 服务是从 Intent 里读那两个许可的, 所以设置页拨完发一条
  `ACTION_REFRESH` —— 打开时顺手把常驻铺开、关掉时把已经在跑的那半条收回来。没有它, "我打开了
  它却要等我关掉再打开一次"就是个说不通的中间态
- **重启应用要把监听恢复起来**: 许可是存盘的, 所以 `MainActivity.onCreate` 里调一次
  `LwWakeWord.ensure()` —— 否则"允许唤醒"只是个记号, 服务不会自己起, 而主人按下它的意思显然是
  "让它听着"
- **半双工那道闸开合时通知栏要改**: `listeningText()` 里那句"正在念回答, 先不听"是主人的纪律
  (静音是一个状态, 不是一个看不见的副作用), 而闸是 `LwSpeak` 那侧合上的、不会回来叫我们 —— 所以
  服务里有一个 400 ms 的观察者盯 `VoiceState.speaking` 那一跳, 只在真的变了时才重发通知
- **`ACTION_STOP_VOICE`**: 会话界面那个胶囊只能关常驻那半条 (它代表的就是这件事), 唤醒词接着守;
  整件事收工是通知栏那个「停止」。没有这一条, 点一下胶囊就等于再也不听了

**另一个错换了个触发口, 静态走查 `LwModes` 时抓到的**: 视频模式原来顺手把 `allowWake` 也写成 true
(`setAllow(context, true, true)`) —— 也就是**切一下模式就把主人在设置页关掉的那个「允许唤醒」重新
打开**。它与被修掉的那个错是同一类: 拿别人的决定去做一件他没要求的事。现在的规矩是**一个许可都不许
自己打开**: 唤醒词那一个只读来用, 关着时如实说"是那个开关挡着, 到设置页去开"; 而常驻语音那一个本来
就是"视频模式是说话为主"的语义, 所以只有它允许由这条路打开。手机模式那一侧对称: 只收回常驻语音,
唤醒词连读都不读 —— 否则就是"切个模式, 设置被悄悄改了"。

**注意**: 步 2 与步 3 之间的中间态 (KWS 起着而 `openVoice()` 没接通) 不会出现 —— 两步是同一次改的,
而且 `openVoice()` 缺 VAD / 缺 ASR 模型时都只记原因、不拦唤醒词 (与原来那条"尽力而为"一致)。

**走查 diff 时抓到的一个自相矛盾 (2026-10-05)**: 第一稿把 `if (!voiceEnabled) return` 写在 `openVoice()`
开头, 而"允许常驻语音"缺省是关的 —— 于是那条链**永远不会开**, "喊一声然后说话"这个功能整个不工作。
它的文案还写着"关着时开口说话没人应", 把它当成设计而不是 bug。现在分成两件事: 一次命中**永远**开门
([sticky] = false, 闲置超时收回去), 那个许可只决定**留不留着** ([sticky] = true)。教训是这类"许可"
很容易被写成"连基本功能一起关掉"——许可该关的是**代价** (一直占着麦克风与 240 MB), 不是那个功能本身。

## 六、交互延迟: 说话结束到发出去的等待 (2026-10-05 已实装)

主人反馈"常驻语音里说话结束到发送, 等待的时间较长"。拆开是四段, 而**最大那段只由 VAD 的一个数决定**:

| 那一段 | 原值 | 现在 | 怎么来的 |
| :-- | :-- | :-- | :-- |
| VAD 等够静音才交段 | 3.0 s | **0.8 s** | `SpeechSegmenter.MIN_SILENCE_SECONDS`。它同时定"等多久"与"段尾有多长": sherpa 的 `voice-activity-detector.cc` 非语音分支里 `end = buffer_.Tail() - MinSilenceDurationSamples()` |
| 头一句的识别器加载 | 一到几秒 | **与说话重叠** | 命中唤醒词那一下 `preheat()` 另起线程 `LwSpeech.warmUp()`, 那笔账落在主人还在说话的那几秒里 |
| host 轮询队列 | 500 ms | **150 ms** | `VOICE_POLL_MS`。一次 tick 只是一次 `stat` |
| SenseVoice 认那 3 s 静音 | 段里含 0.4-0.9 s | 未改 | 裁尾部静音收益最小而唯一那条风险是咬掉最后一个字, 先不做 (要真做, 必须按"能量"裁而不是按固定时长裁) |

合计大约从 3-4 秒压到 1 秒出头。三个数各有各的落点, 别抄到第二个地方去:

- `MIN_SILENCE_SECONDS` 只在 `SpeechSegmenter` 里 (说话中间停顿长的人会被切成两段, 真机上真被切了
  就调回 1.0-1.2 s)
- `VOICE_POLL_MS` 只在插件里
- 那声短提示音现在也占住半双工那一小段 (`hit()` 里 `beep` 前后置 `speaking`), 否则它会被麦克风录进去,
  主人紧接着说的第一句话就带着一声"嘀"进识别器

## 七、怎么判它对了

四条判据, 每条都能在真机上跑出来。

### 判据 1: 致命组合已经不可能出现

打开设置页那个开关之后, 这三件事必须同时成立:

```
lw_wakeword op=status   →  listening: true
                        →  capturing: false        ← 这一条是新的, 也是最要紧的
                        →  vadReady: false
通知栏                    →  只有"正在听「…」", 没有"常驻识别在跑"
```

只要出现"设置开关开着 + `capturing: true`"的组合, 就是没改对。

### 判据 2: 冷启动顺序 (KWS 先行, ASR 随后)

从 `op=stop` 的干净状态开始, 全程看一条日志:

```
adb logcat -s LwWakeWord DshHost
```

期望的顺序是 **起服务 → 只有 KWS 起来 → (几小时后) 命中 → 才出现切段器与识别器**。
`logcat` 里 VAD 与 SenseVoice 那两行必须出现在 `heard …` **之后**。反过来 (先出现) 就是顺序还是错的。

### 判据 3: 电量与内存 (两条链的代价真的分开了)

分别量两段, 每段 1 小时, 同一块屏、同样的亮度:

| 段 | 配置 | 看什么 |
| :-- | :-- | :-- |
| A | 只 KWS (`允许唤醒` 开, `允许常驻语音` 关) | `lw_battery` 的百分比差、`lw_power` 里本应用的耗电 |
| B | 常驻语音全程开着 (命中一次让它进来, 不让它超时) | 同上, 外加 `dumpsys meminfo` 的 PSS |

期望: **A 显著低于 B, 且 A 里识别器那 240 MB 不在内存里**。判 A 的时候 `meminfo` 里不该看到
SenseVoice 那一份占用 —— 这一条比电量曲线更硬, 也更快量出来。
另有 `lw_keep_awake` 可以先借来做对照 (但它是 `PARTIAL_WAKE_LOCK`, 与这条链不是一回事, 只当参考)。

### 判据 4: 隐私指示器与真实状态一一对应

三处可见的地方, 状态必须与"哪条链真在跑"对得上:

| 可见处 | 只 KWS 时 | 常驻语音也开着时 |
| :-- | :-- | :-- |
| 通知栏那条常驻 | 在, 只说在听哪几个词 | 在, 多说一句"常驻语音在跑" |
| 输入框上沿那个胶囊 | **不出现** | 出现, 点一下停 |
| 系统状态栏的麦克风指示 | 只在 KWS 采集时出现 (这一个是系统画的, 改不动) | 同样出现 |

第三行要说清: **系统那个指示器分不出 KWS 与 ASR**, 只要麦克风开着它就亮。所以"常驻麦克风暴露隐私
指示"这件事在只跑 KWS 时**照样成立** —— 想彻底不亮只能整条链停掉。这一条不是靠改代码消除的,
是要在设计上说清: 允许唤醒 = 系统那个小圆点一直亮, 这是那个许可的代价, 所以它必须在设置页上写明。

### 反例 (改完仍然算错的样子)

```
设置开关开着 → capturing: true              判据 1 失败, 耦合还在
先出现 SenseVoice 加载 → 后出现 heard        判据 2 失败, 顺序还是反的
A 段与 B 段电量差不多, A 段内存里有识别器      判据 3 失败, 代价没分开
纯 KWS 态下通知栏写"常驻识别在跑"或胶囊跳出来   判据 4 失败, 界面在替人宣称
```

### 判据 5: 唤醒之后的头一句落在新对话里

```
lw_voice op=inbox   →  delivery.sessionId 与命中之前那个不一样
                    →  delivery.steered 没有涨 (新对话里没有正在跑的轮可插)
```

而且**第二句必须回到老规矩**: 一次唤醒里说了两句, 第二句要进**同一个**新对话, 不是再开一个。
反过来 (说两句话开出两个对话) 就是"唤醒窗口"那个标记没收干净。

**2026-10-06 改口径**: 这一条作废 —— 时间窗内 (2026-10-07 起 20 分钟, 2026-10-11 起 10 分钟) 唤醒之后的头一句与点球
一样落回同一场 (两句话当然也
在同一场), 只有小时过了才新开一场, 见 `docs/floating-input.md` 与 `tools/check-voice-inbox.mjs`。

### 判据 6: 半双工 A 的两条边

念回答那一段 (`lw_voice op=say`) 与它前后各说一句, 三件事都要成立:

- 念的期间通知栏**明说**"正在念, 先不听" (不是静默地什么都不做)
- 念的那句话**没有被录进去** (`lw_voice op=inbox` 里不该出现回答的正文)
- 念完之后说的那一句是**完整的一句**, 开头不带念之前那半句 (切段器在闸合上时 `abandon()` 过)

第二条与第三条一起才说明"半双工是一道单独的闸", 只满足第二条 (把 `add(vad)` 拿掉) 会在第三条上
露馅。

> **第二条 2026-10-09 在真机上真的红过一次**: 用**在线引擎**念回答时它被整段录进去、又投成 #24
> (见上面那条注记) —— 病根不是判据错, 而是那道闸的输入 (`VoiceState.speaking`) 只被两条引擎写过。
> 所以这一条现在的做法是"三条引擎都写标记 + 判据取并集", 任何一条新引擎忘了写也还关得住

## 八、那条 use-after-free: 开一次窗口为什么会让整个应用重启 (2026-10-06 修)

主人报的是"键盘输入有概率点不出语音, 而这时候去菜单里点「说话」再点一次, **整个应用重启**"。真机
的崩溃日志把第二半说清了 —— 2026-10-05 到 10-06 一共七次, 全是同一个栈:

```
Fatal signal 11 (SIGSEGV), fault addr 0xf8, tid (lw-audio-captur)
  #00 libsherpa-onnx-jni.so
  #01 Java_com_k2fsa_sherpa_onnx_Vad_acceptWaveform
  ... SpeechSegmenter.accept <- WakeWordService.halfDuplex$lambda$0 <- AudioCapture.loop
```

**病根是"关窗口时把切段器放掉了, 而采集那条线程还会再走进去一次"**: 那台消费者是
`closeVoice()` 里 `remove`、`openVoice()` 里 `add` 的, 而 `AudioCapture.loop` 是**一边遍历一边调**
的 —— 关掉那一刻正被调用的那一个已经拿到手, 于是它在 `vad.release()` 之后仍会走进去,
`SpeechSegmenter.accept` 里的 `vad.acceptWaveform` 就成了对一块已释放内存的调用。进程当场死, 系统
把服务与界面拉起来, 看起来就是"应用重启"。

修法两条, 缺一不可:

1. **消费者与采集同生共死**: 那台 sink 现在只在 `startListening()` / `stopListening()` 里挂上摘下
   (`voiceSink`), 而"这一句话的窗口开着没有"由 `vad` 那**一个引用**说。`closeVoice()` 的顺序因此是:
   **先 `vad = null`, 再 flush 与 release**（`flushVoice()`）—— 采集那一侧下一帧看到的要么是 null
   （干脆不转发）, 要么是一个活着的切段器
2. **`SpeechSegmenter.close()` 幂等** (`closed` 记号, `@Volatile`), `accept` / `flush` / `abandon`
   三个入口都以它为闸: 重复收尾不许第二次碰原生

兜底还有两条 (它们不是主修, 是"万一还有别的崩法"): `LwWakeWord.speakNow` 里有个**只活在进程里**的
记号 —— 连着两次在开窗口之后 30 s 内又把进程带走, 这一版就不再自动开, 并回一句人话
(`WakeWordState` 与 `VoiceState.lastError` 里都留痕), 而窗口正常收工那一次会把这个计数清掉; `OverlayService.fend()`
那两次 `startForeground` 也都兜住了 (类型被拒退 `specialUse`, 再拒就走 `fail()` 正规收场)。

**模拟器上量不了这一条**: 那台 x86_64 模拟器上 `libsherpa-onnx-jni.so` 在 linker 里就崩
(SIGSEGV @ `dlopen`), 与这里的 use-after-free 不是同一件事。所以这一条的判据是**真机上不再出现
那条栈**, 而"开窗口 / 关窗口反复切"这件事只有在真机点得出来。
