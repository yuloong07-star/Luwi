# 浮窗输入（把 dsh 的输入框浮在别的应用上面）

主人要的不是"整个应用浮上来"，而是**在别的应用里也能直接跟 dsh 说话**。这份文档记的是第一版
（面板 A）：窗里装整个 GUI，能拖、能收起、能打字，会话与主界面共享；下一版（面板 B）再由客户端
插件把聊天区收掉、只留输入条。

## 一、为什么这么做

- **浮在别人上面是 Android 的事**：`WindowManager` + `TYPE_APPLICATION_OVERLAY`，需要
  `SYSTEM_ALERT_WINDOW`。本机这条特殊访问早就给了（`lw_permissions` 的「悬浮窗: 已允许」），
  清单里 `MANAGE_OVERLAY_PERMISSION` 也声明着，缺的只是代码。
- **"输入框"是页面的事**：dsh 的输入框活在 GUI 页面里。所以第一版直接把那个页面搬进浮窗 ——
  同一个 host 的第二个客户端，会话、cookie、localStorage 与主界面共享，页面上的输入框、麦克风
  按钮（语音输入）、朗读按钮（语音输出）在窗里照常可用。

## 二、这一版有什么

| 部件 | 行为 |
|---|---|
| 标题栏 | 按住拖动整个窗；左边写着应用名与当前状态（「Luwi · 正在听 · 视频模式」） |
| 收起 | 把输入条摘下来，留那颗球（2026-10-05 起：收起不再是把窗压成一条） |
| 应用 | 把主界面拉到最前（`CLEAR_TOP`+`SINGLE_TOP`，不另开一页） |
| × | 关掉浮标（服务停、球与通知一起收，存盘的「浮标一直在」也一起关掉） |
| 页面 | 指向 host 报出来的那个带 token 的地址，与主界面是同一个 GUI |

通道方法 `overlay`：`show`（可带 `expand=true`，另有 `width`/`height`/`x`/`y` 给输入条，单位像素）、
`expand`、`collapse`、`hide`、`state`、`phase`（宿主推那一句，见第七节）；工具侧是 `lw_overlay`。

## 三、三条必须记住的限制

1. **窗是可获焦的，所以窗外不再穿透**。要收系统输入法，就不能给窗口加 `FLAG_NOT_FOCUSABLE`；
   代价是手指落在窗外会被窗口吃掉。窗做小一点是唯一的补偿（面板 B 会更小）。
2. **浮窗挂在长跑的前台服务上**，通知栏有一条常驻通知（点它回应用，通知上的按钮直接关浮窗）。
   后台起步时前台服务类型里带 `microphone` 那一半可能被系统拒（持有 `SYSTEM_ALERT_WINDOW` 是
   官方豁免之一，但不是每个 ROM 都认），拒了就退到 `specialUse` —— 前台时麦克风照常，后台可能
   拿不到音频，这一点如实写在 `OverlayService.fend()` 里。
3. **锁屏之上不要指望它**：keyguard 上画可交互的窗另有条件，这一版没去碰。

## 四、验证判据

- `lw_overlay op=state`：`overlay permission: granted`、`host:` 是那个带 token 的地址。
- `lw_overlay op=show`：屏幕上出现浮窗，页面是 dsh 的界面；拖标题栏能挪；收起/展开能切。
- 窗里点麦克风说话：草稿框出现文字（这条依赖语音输入那一支：`feat/voice-output` 上的
  `lw-native` provider 与模型已就绪）。
- `lw_overlay op=hide`：窗与通知一起消失。

## 五、与其它分支的关系

```
main
└── feat/voice-input    麦克风授权 + 本机离线转写 (sherpa-onnx/SenseVoice)
    └── feat/voice-output 读出 (系统 TTS) + 页面朗读那一行
        └── feat/overlay  本文件: 浮窗 (面板 A)
```

编译这一条分支就同时有读入、读出与浮窗。装机仍用同一个 debug keystore 覆盖安装
(`pwsh -File tools\lw-install.ps1`)，否则只能卸载重装、`files/dsh-home` 里的会话与记忆会一起没。

## 六、下一步（面板 B）

B 不换地基：还是这个窗、这个服务，只是**加载带参数的地址**，另加一个 DSH 客户端插件：在那个
参数下把聊天区藏掉、只渲染输入条（+ 麦克风按钮），窗也跟着变成一条。这样做的好处是输入条由
页面自己渲染，输入法、语音、发送全走同一条链路，不需要在原生里重接 DSH 的会话协议。

## 七、浮标（2026-10-05 实装：一颗球 + 按需展开的输入条）

面板 A 的窗还在，但它不再是"一直在的一块窗"，而是**按需展开的那一条**；平时屏幕上只有一颗球。

### 两块窗，不是一个标志

| 窗 | 何时在 | flags | 谁吃触摸 |
|---|---|---|---|
| 球（`BallView`，48 dp） | 常驻 | `FLAG_NOT_FOCUSABLE \| FLAG_NOT_TOUCH_MODAL \| FLAG_LAYOUT_IN_SCREEN` | 只有球那 48 dp；窗外照旧给底下的应用 |
| 输入条（那块 WebView） | 展开时挂上，收起时**从窗口上摘下来** | `FLAG_LAYOUT_IN_SCREEN`（**不加** `NOT_FOCUSABLE`） | 它可获焦，所以展开期间窗外不穿透（要收系统输入法就只有这一条路） |
| 菜单（长按出来） | 菜单开着时 | `FLAG_NOT_TOUCH_MODAL \| FLAG_WATCH_OUTSIDE_TOUCH` | 点外面时收到 `ACTION_OUTSIDE` 自己关掉，而底下那个应用不会被顺手按一下 |

**为什么是两块窗，而不是运行期改 `FLAG_NOT_FOCUSABLE`**：那个标志在各 ROM 上改起来行为不一
（有的要摘掉再加一遍），而加窗/摘窗没有这个不确定面；输入条的页面实例留着（摘下来再挂回去不必
重载），所以 WebView 是建一次、用很多次。

### 手势与菜单

- **点一下是一个四段开关**（2026-10-05 主人点名的点击序列 + 追加的"念回复时再点一次球可停止播报"，
  状态机是纯函数 `BallTouch.act`）：
  - **半隐收着时点一下 = 只召出**：球滑回来，**不碰语音链**
  - **召出之后再点一下 = 进语音输入**：走应用侧那条识别链（`LwWakeWord.speakNow` →
    `ACTION_LISTEN_NOW`），**不用页面自己的麦克风** —— 球、输入通道与主页共用同一个识别器。它与
    唤醒词命中同一档：开一次"讲一句话"的窗口，闲置 10 s 收回去（**视频模式下那一档是常驻的**：那
    个模式要求这一路留着，见 `docs/wake-word.md` 第五节）
  - **正听着的时候再点一下 = 收回来**（`LwWakeWord.hushWindow`，与输入框上沿那个胶囊同一个动作：
    收掉这一句、唤醒词接着守），再点又能开始 —— 同一个球可以反复切换。
    **名字 2026-10-06 从 `stopVoice` 改过来的**: 它收的从来不是"常驻那一半", 而是主人此刻在说的
    那一句
  - **正在念回答的时候点一下 = 掐断播报**（`LwSpeak.stop()`，两条引擎都停并顺手把半双工那道闸放
    回去）。这一档压在"正听着"**前面**：念的时候麦克风整条被闸掉了，那时人真想按的就是"停"
- **三击 = 打开键盘输入那块框**（主人 2026-10-07："加上三击 ball 打开键盘输入，ball 菜单的键盘输入
  可以删除"）：三下**连着**（每一下都贴着上一记，双击窗口 300 ms 之内；判据是
  `BallTaps.kind(word, now, lastTapAt, chain)` 那个纯函数）就把那块自己画的文字框张开并把焦点给输入框。
  **净效果是"头两下的轻动作照旧 + 开框"，而开麦那一步 2026-10-10 起被确认窗挡掉了**（见下面那条
  「确认窗」）：原来三击是先开麦、第三下再收掉、然后才弹键盘，那一次来回会主线程建一遍切段会话
  （主人："三击 ball 会打开语音输入，并且会卡一下"）。现在头一下那个开麦待办会在第三下当场取消，
  `hushWindow` 只在**别处真的把麦克风开起来**时才走（比如三击之前球上写着「正在听」——那一档点一下
  是收麦），最后 `openChannel(focus = true)`。**四连击也算三击** —— 那只是主人多戳了一下
- **这四下都不出声**（主人 2026-10-05：关于球的所有操作都不要有提示）：结果照旧记一笔进
  `OverlayState.lastHint` 与 `adb logcat -s LwOverlay`，`lw_overlay op=state` 的 `said` 读它 ——
  "不出声"不等于"查不到"。**不成功的那几种仍会说**（缺权限 / 缺模型 / 悬浮窗被拒 / 收件箱写不进去）：
  那些不说的话，点一下就是"什么都没发生"
- **双击 = 打断**（2026-10-06 主人加的那一支）：球上写着**正在想**时，**300 ms 之内点两下**
  （`BallMinutes.DOUBLE_TAP_MS`）＝ 打断状态与那一轮 —— 球那一侧写一句命令句
  （`VoiceCommands.INTERRUPT` = `打断当前回答`）进收件箱，宿主插件认出它就把浮标那一场正在跑的轮
  `agent.cancel({kind:'user'}, {keepInbox:true})` 掉，并顺手把 `phase` 推回 `idle`（见
  `docs/wake-word.md` 那张命令表与 `host-plugin` 的 `runVoiceInterrupt`）。
  **它只在"正在想"那一档**：正在念时点一下是掐断播报、正在听时点一下是收回来，那两下本身就是主人
  要的，不该改成两下的。**"正在想"里的单点被推迟 `BallFeel.thinkingTapMs()`**（防误触档 530 ms，见
  `OverlayService.pendingTap`）：不等过双击窗口的话，双击的第一下会先走那一档的单点动作（收/开语音
  窗口），于是"想打断"变成了"开了麦克风"
- **两档防连击**（同一天主人点名的两个数，判据是纯函数 `BallTaps.guard`）：
  - **正在听那一档 1 s**（`BallMinutes.LISTEN_GUARD_MS`）：那一档的点击是"把语音输入收回来"，而开语音
    那一下也是点球 —— 手抖出第二下就是"刚开就关"。1 s 之内的第二下**只记一次账**（什么都不做）
  - 其余状态仍是 **350 ms**（`BallMinutes.TAP_GUARD_MS`，2026-10-06 报的"点一次可能直接打开语音输入"）
  - **双击窗口（300 ms）比防连击窗口（350 ms）窄是有意的**：前者回答"这两下算不算一次双击"，后者回答
    "第二下要不要当没发生"。于是 301 ms 那一档的第一下会在 300 ms 后做原来的动作、第二下被防连击吃掉
    —— 既不打断也不切换，行为是确定的
- **确认窗：只有"开麦"那一下排队，其余动作当场做**（2026-10-10 主人："三击 ball 会打开语音输入，
  并且会卡一下"）：单击的动作原来在 UP 那一刻全部当场执行，于是三击的头一下就能把麦克风打开。现在
  判据挪进纯函数 `BallCommit.deferMs(act, word, summonFresh, replyBox, feel)`：**要开麦**那几支
  （正在想 / 失败 / 有回复框 / 刚召出）挂成一个待办（`OverlayService.pendingTap`），等
  `BallFeel.commitWindowMs`（= 双击窗口，防误触 220 ms / 标准 300 ms）——"正在想"那一档仍用更晚的
  `thinkingTapMs`。窗里来了双击或三击就**当场取消**（`OverlayState.tapCommitsCancelled` 记一笔），
  到点时再算一次 `BallTouch.act`，已经不是开麦就作废（免得替别人把麦克风关掉）。
  **召出 / 收麦 / 掐播报一律不等**：那三下是"跟手"与"别说了"，晚一档比多开一次麦糟得多。
  待办的生命周期由 `onDestroy` 里那句 `handler.removeCallbacksAndMessages(null)` 兜住
- **按下这一瞬间回一记轻触觉**（`HapticFeedbackConstants.CONTEXT_CLICK`，2026-10-10）：补偿确认窗
  那 220/300 ms 的等待感 —— 它与长按那一记用同一个 API，跟着系统的"触摸反馈"开关走，不要权限
- **"开了又关"走静默快径**（2026-10-10，`VoiceRollback.isFast` + `WakeWordService.VOICE_ROLLBACK_MS`
  = 300 ms）：开门那一步里"预热识别模型"与"把通知栏改成『听着你说这一句』"两笔都延迟 300 ms 再做，
  这一段里收窗且**一个人声都没听到**就把那条待办摘掉 —— 于是开了又关只留一次状态回退，既不闪通知
  也不白读一次模型。**收尾一步都不省**（切段器 flush/close、转写线程、识别器 reap 照旧）。
  两个读数在 `lw_wakeword op=status`：`fastRollbacks`（走了快径几次）与 `shortLivedOpens`
  （开麦之后 500 ms 内就被收掉几次，**确认窗落地之后它应该趋近于 0**）
- **长按 = 菜单**（震动一下作回应）：返回应用 / 关掉浮标（有人占着相机时中间多一行「释放视频模式」）。
  **「返回应用」那一行 2026-10-07 加的**（主人："ball菜单里加上返回应用按钮"）：走
  `OverlayService.returnToApp` → `openApp` —— **有轮在跑时落到正在想的那一场，没有在跑的轮就是一场
  新对话**（2026-10-11 主人："ball菜单栏里『回到应用』要改成走的是正在想的对话，没有则返回新对话"），
  同时**顺手把框收起来**。**它与双击回复框从 2026-10-11 起是两套去向**：双击那条仍走这块框跟哪一场
  打过交道（见下面「回应用那一跳」）
  **「键盘输入」那一行 2026-10-07 拿掉了**（主人："加上三击 ball 打开键盘输入，ball 菜单的键盘输入
  可以删除"）：同一个去向挪到了**球上三击**（见上面那一条）
  **「说话」那一行 2026-10-06 拿掉了**（主人的话："已经可以用点击的方式使用就没必要留着"）：点球那套
  两段点击一直都在（见上一条），菜单再放一个入口就是同一件事的第二扇门。
  **「识屏模式」那一行 2026-10-08 拿掉了**（2.5.0 批次 4：那个模式整个摘掉）：它当年是识屏那一档
  唯一的界面入口（`toggleScreenMode` → `askMode(mode, said)`，"开"= `打开识屏模式`，"关"= `退出识屏
  模式`）—— 而"用户得先切一个模式，模型才看得见屏"正是那一批要消掉的心智负担：现在那句话只要指代
  不明（这个 / 屏幕上 / 照片里…），投递前就会自动附一张主屏截图（设置页「截图」段那一条，缺省开）。
  说"打开识屏模式"不再被当命令（照普通一句话进会话），说"退出识屏模式"仍然等于收工回手机模式。
  **「回应用」那一行 2026-10-07 又拿掉了**（主人："双击回复框相当于回应用，ball 菜单的「回应用」选项
  可以删掉"）：同一个去向挪到了**回复框上双击** —— 那块框里最新那条回复是哪一场发来的，双击就回到
  哪一场（见下面「回应用那一跳」）。它做的事比"把应用提到前面"多一件 —— 顺带把会话界面带到那一场
  对话上。**同一天它又以「返回应用」的名字回到菜单第一行**（同一个去向、同一份实现）。**模式那两行更早就拿掉了**（主人 2026-10-05：默认手机模式，菜单里不要模式选择
  项），模式仍由 `lw_mode` 工具与"说出来"那句命令切，菜单标题上那个模式名照旧写着，所以"现在在哪一档"
  还是看得见。**「一直听: 开·关」那一行 2026-10-06 也拿掉了**：它能在手机模式下把常驻识别链打开，
  于是对话一直进行下去 —— 主人判定多余的两个入口就是它与设置页那个开关；现在只有视频模式能要求那一留

### 回应用那一跳（2026-10-06 主人点名）

**入口 2026-10-07 挪到了回复框上双击**（主人："双击回复框相当于回应用，ball 菜单的「回应用」选项可以
删掉"）：双击就回到**往这块框输入投给了哪一场**（`OverlayState.viewSession` → 优先 `inputSession`）；
从没从框里发过话时退回"最新那条回复是哪一场发来的"（`replySession`）；两边都没有就**进新会话界面**
（2026-10-09 主人："这里没有（还没发过话）就进入新会话界面"）。手势挂在**回复那一块**上，输入框那一半
的双击仍是"选中一个词"。**菜单里那行「返回应用」是同一个动作的第二扇门**（2026-10-07 主人要的）。

**"对应会话"= 我发出去的那一场，不是"最后推回复进来的那一场"**（2026-10-09 主人："当前是回到最近在
ball 输入会话的那一场。改为谁发送了输入框，就回到那一场"）：一块框可以先后跟好几场说话 —— 第一次
按浮标那本 10 分钟的账投给 `dsh-ball` 那一场，之后再打开别的会话、它的一轮结束也会把回复推进这块框，
于是 `replySession` 变成了那一场。原来双击就按它走，主人要回去的是**自己那次输入投出去**的那一场。
两笔账因此拆开：`inputSession` 由 `OverlayService.ask` 在写收件箱那一刻记下实际用的 `to`，
`replySession` 只留"框里显示的是谁的话"（`replyTarget()` 仍按 `inputSession` 优先取投递目标，所以点球
说的那一句也回到同一场）。优先级是纯函数 `BoxTarget.choose`，判据在 `BallTest`。

**两笔账都空着 = 新会话界面，不再读浮标那本账**（2026-10-09 主人）：原来最后一档是"落回浮标账本"
（`VoiceInbox.currentSession` → `voice/session.json`），那是"浮标上一轮说话的地方"；而"我还没从这块框
发过话"要的是**一场新的会话**，不是浮标上一轮的落点。三个入口（双击回复框 / 菜单「返回应用」/ 点通知）
都按同一条走。

**2026-10-11 两扇门分开：菜单那行走"正在想的对话"，双击回复框那条不变**（主人当天先报现状、再点名要
什么："回到应用走的是正在想的对话，与回复框不一样" → "ball菜单栏里『回到应用』要改成走的是正在想的
对话，没有则返回新对话。而双击回复框现在不变，仍返回现在的发送回复的对应对话"）。判据抽成纯函数
`ReturnTarget` 两个入口（判据在 `BallTest`）：

- **球菜单那行「返回应用」（与常驻通知那条路）走 `ReturnTarget.menu`**：**只看有没有轮在跑** —— 有就是
  球上写着「正在想」的那一场（`OverlayState.runningSession` = `ball-phase.json` 里 `startedAt` 最大的
  那一条，连"宿主没在跑就不采纳"那道闸都与球上那三个字同一个），**没有就是一场新对话**（`openApp(null)`
  给的是 `BallReturn.NEW_SESSION`）。**它与"这块框刚才是跟谁说话"无关** —— 按「返回应用」要看的是
  "它现在在给谁干活"
- **双击回复框走 `ReturnTarget.replyBox`**（2026-10-09 那套，一个字没改）：投出去的那一场
  （`inputSession`）→ 最新那条回复是谁推来的（`replySession`）→ 框上一次跟谁打过交道（`boxSession`）→
  一个都没有才是新会话界面

**`boxSession` 那一笔 2026-10-11 补上**：给双击那一条兜底的。病根是**这块框把话发出去就自己收掉**
（2026-10-06 的口径），而按的时候它本来就是关着的 —— `inputSession` / `replySession` 早跟着
`closeChannel()` 清空了，于是那一跳落的其实是"新会话界面"：删掉 `dsh.sessions.current` 再重载，而 dsh
那一侧的新会话落在**最近动过的那一场的工作区**上，哪一场在跑界面就跑到哪一场去。现在多一笔
`OverlayState.boxSession` = "这块框最后跟哪一场打过交道"（**只在框真的跟某一场说过话时才写**：从框里
投出去的那一句记下实际用的 `to`，落进框的那一条回答记下它的来源；`closeChannel()` **不动它**）。
读数在 `lw_overlay op=state` 的 `boxLast` 与 `boxTo`（双击那一条的落点）、`menuTo`（菜单那一条的落点）。

同一批里**常驻通知那条路不再写死会话 id**：那个 id 是**建通知那一刻**抄进 `PendingIntent` 的附加数据
里的，而通知只在球上那三个字变化时才重建 —— "框里落进一条回复"并不改那三个字，于是点通知很容易落到
上一条那一场，与菜单那条路各答各的。现在它多带一个 `EXTRA_OPEN_LIVE`，由 `MainActivity.requestedSession`
在**收到 intent 那一刻**现问一次 `OverlayState.runningSession()`（与菜单那行同一套口径）；读不到
（冷启动，进程是新起的一份）才退回 intent 里那个 id。两条路于是永远答同一场。

**两条入口都顺手把框收起来**（2026-10-07 追加）：主人报的是"在 dsh 应用里双击回复框没有任何反馈" ——
界面本来就在那一场时，切会话那一步什么都不用做（JS 回 `already`），屏幕上于是没有一点动静。收掉这块
框就是这一下无论如何都看得见的那一半；需要切场时它让开的正是会话本身。

**回到哪一场**：会话界面自己记着"正在看哪一场"，而那是**浏览器里的路由状态**
（dsh 客户端的 `localStorage['dsh.sessions.current']`，值形如 `{"sessionId":"session-…"}`），它只在页面
启动那一步读一次（`ui-workspace` 的 `restoreSelection`）—— 所以"把界面放到前面"与"让界面切到那一场"
是两件事：

| 那一半 | 实现 |
|---|---|
| 哪一场 | 双击回复框用 `OverlayState.viewSession`：优先"我发出去的那一场"（`inputSession`），没有就退回"最新那条回复是谁推来的"（`replySession`），再没有就用"这块框最后跟哪一场打过交道"（`boxSession`，2026-10-11 加 —— 框收掉之后那两笔是空的，而按的时候它本来就关着），三个都空才 = **新会话界面**（`BallReturn.NEW_SESSION`，空串那个记号）。**球菜单那行「返回应用」与常驻通知走另一套**：正在想的那一场，没有就是新会话界面（2026-10-11 主人分开了这两扇门） |
| 交给谁 | **两条路一起走**（2026-10-07 补上第二条）：`OverlayService.openApp` 把请求直接写进同进程的 `BallReturn`（界面活着时立刻生效），同时 `startActivity` 带 `open-session` 把任务提到前台（intent 那一条由 `MainActivity.onCreate` / `onNewIntent` 收）—— 不把成败押在 `onNewIntent` 上 |
| 请求长什么样 | `BallReturn.Request(session, seq)`：**seq 自增**，所以同一个会话连点两次也一定是一次新请求（Compose 的状态在值没变时不重组，那是"第二下静默什么都不发生"的根） |
| 怎么切过去 | `HostScreen` 的 `LaunchedEffect(请求.seq)`：页面没落在 http 上就等 `onPageFinished`，然后跑一句 JS —— 带 id 就改 `localStorage['dsh.sessions.current']` 再 `location.reload()`，**重载完读回那个键验证**；空 id（新会话）就只删那个键再重载（`BALL_NEW_SESSION_JS`），dsh 自己会开一场新的（那一档没有 id 可对，做完就算成）。一次不成再试一次，两次都不成才把请求放掉 |
| 怎么看见 | 手势、请求、JS 的 `already` / `reload` / `failed`、验证结果都进 `OverlayState.lastHint` 与 logcat（`adb logcat -s LwOverlay DshWebView`），`lw_overlay op=state` 的 `said` 读它；**设置页那一层收到请求先把返回栈 pop 回主页**；常驻通知那条 content intent 也带上这一场（点通知 = 完整的回应用，而且它是用户手势，不受后台启动限制） |

代价与边界：**要重载一次页面**（那个键只在启动那一步读），GUI 里没发出去的草稿会没；两笔会话账都空着
时不再猜一个 id，走的是"删键 + 重载、让 dsh 自己开一场新的"那一条

### 时长：一处来源，两笔账

`overlay/BallMinutes.kt` 是浮标这一摊唯一的一份时长表（主人的要求：时间参数集中定义，不用散落的
魔法数字）。两个数**不一样**是有意的 —— 混成一个的话"提示消失"与"球收边"会同时发生，看着像球自己
闪了一下：

| 常量 | 值 | 管什么 |
|---|---|---|
| `BallMinutes.NOTE_MS` | 3 s | 状态提示显示多久（主人点名的"3 秒"） |
| `BallMinutes.PEEK_IDLE_MS` | 5 s | 最后一次活动之后多久收边（主人："4s 改为 5s，其它不变"） |
| `BallMinutes.EDGE_SNAP_MS` | 200 ms | 收边 / 滑回来那条动画 |
| `BallMinutes.IME_SETTLE_MS` | 400 ms | 收起输入条之后等一拍再摆球 |
| `BallMinutes.TAP_GUARD_MS` / `BALL_TAP_GUARD_MS` | 350 ms / 450 ms | 两次点球之间的防连击窗口（标准档 / 防误触档，2026-10-09 防误触档放宽） |
| `BallMinutes.DOUBLE_TAP_MS` / `BALL_DOUBLE_TAP_MS` | 300 ms / 220 ms | "正在想"里算双击的窗口（那一档双击 = 打断；标准档是主人点名的 0.3 s，防误触档收窄） |
| `BallMinutes.LISTEN_GUARD_MS` / `BALL_LISTEN_GUARD_MS` | 1 s / 1.5 s | "正在听"那一档的防连击窗口（标准档是主人点名的 1 s，防误触档放宽） |
| `BallFeel.commitWindowMs` | 300 ms / 220 ms | **确认窗**（2026-10-10）：只有"要开麦"那一下排队等它，窗里来了双击/三击就取消；取值就是双击窗口（过了它就不会再有双击或三击） |
| `BallMinutes.BALL_PRESS_BASE_MS` + `BALL_PRESS_MARGIN_MS` | 500 ms + 150 ms | 防误触档的长按门槛 = `max(平台 longPressTimeout, 500) + 150`（典型设备上仍是 650 ms）；标准档直接用平台那个数。**原来这里写死 650 ms**，2026-10-10 改成从平台值派生，两档不再是差一倍多的尺度 |
| `BallMinutes.BOX_IDLE_MS` | 20 s | 输入通道那块框没人碰多久就自己收（收掉之后球那一笔账从零起算） |
| `WakeWordService.VOICE_IDLE_MS` | 10 s | 一句话的闲置自动关闭（在识别链那一侧；**视频模式那一档不受它管** —— 那个模式要的是留着）。**2026-10-09 起**：还没说到一句时助手的「正在想 / 正在念」期间这一笔账挂起（主人："语音输入没说完自动退出"）；而**一句话投出去之后上限换成 `WakeTuning.SENT_TAIL_MS`（0.3 s）且不再挂起** —— 还在说就继续听（人声续期），停下来就收（主人："发送问题后就可以收掉"） |
| `WakeWordService.VOICE_ROLLBACK_MS` / `VOICE_SHORT_LIVED_MS` | 300 ms / 500 ms | **"开了又关"那条快径的窗口**与"短命的一次"的读数窗口（2026-10-10）：快径里预热与通知那两句一起取消，收尾照常 |

收边那一档的判据只有**一处**：`refresh()` 那 400 ms 一拍读 `lastActiveAt`（`noteActivity()` 记账），
忙的时候不收 —— 有状态词、语音在跑、有人正按着、菜单或输入通道开着，五种都不收。

### 输入通道：那块自己画的 650 px 文字框（2026-10-05 主人点名）

这条入口（2026-10-07 起是**球上三击**，之前是长按菜单里的「键盘输入」）不再展开面板 A 那块 WebView，
而是张开**一块纯原生的文字框**
（`overlay/BoxView.kt`）：打字、回车发送、回答也画在这里，于是问与答落在同一块框里，眼睛不必在浮标
与页面之间来回找。

| 口径 | 实现 |
|---|---|
| 宽 650 px | `BallBox.WIDTH_PX`（主人给的是像素，而"一行 12 字"也是按这条宽度算的） |
| 行数上限 7 行、高度随行数增长 | `BallBox.MAX_LINES` + `BoxView.inputHeight()`（`EditText.maxLines`，到顶之后框里面自己滚）。**2026-10-06 主人追加两行：5 → 7** |
| 回车即发送 | `VoiceInput`（一个自己写的 `EditText`：软键盘走 `onKeyPreIme`、硬件键盘走 `onKeyDown`，两级都吃掉回车） |
| 文本框随浮标移动 | `BoxSpot.x/y` + `layoutChannel()`：拖动每一帧、吸附动画收尾、键盘起来、框自己长高，四处都摆一次 |
| 框外**双击**才消失 | 窗上挂 `FLAG_NOT_TOUCH_MODAL \| FLAG_WATCH_OUTSIDE_TOUCH`，`ChannelRoot` 收 `ACTION_OUTSIDE` → `noteBlankTap()`：**窗口 `BallMinutes.BOX_DOUBLE_TAP_MS`（300 ms）之内的第二下才关**，判据是纯函数 `BallTaps.blankDouble`；**超时的那一下重新起算**（它是新的第一下，不是"第一下的第二下"—— 主人 2026-10-06 把口径从"隔多久都累计的计数器"收窄成真双击）；碰到框或球就把这本账清掉。**发出去了与回答到了那两次自己开关不算它**（那是服务那一侧的动作） |
| 右上角那个 `×` 一点就消失 | **2026-10-07 主人点名加的**："在图标文本框左/右上角加个关闭按钮，点击可关闭"：`BoxView` 由竖排 `LinearLayout` 改成 `FrameLayout`（内容那一层不动，`×` 叠在右上角），点它走 `BoxView.Listener.onClose()` → `closeChannel()`。它是框外双击那一条的第二扇门（全屏应用里不好找空白处，而这个按钮一直在框的角上），**只关框**，不动语音链与球。输入框右边留出 30 dp（`CLOSE_RESERVE_DP`）给它，长句折行不会压到按钮下面 |
| 没人碰 20 s 也自己消失 | `BallMinutes.BOX_IDLE_MS` + `refresh()` 里那一笔账（`OverlayState.boxActiveAt` / `boxIdleMs`）：张开、回复到了、打进一个字、**滚动内容**、摸到框、输入框拿到焦点、**开语音**都续期；到点由 `closeChannel()` 把窗摘下来（**丢一拍再关**：`closeChannel` 自己会再叫一次 `refresh`）。收掉的是窗，**再张回来是一块新框**（回复由宿主再推的那一条补上） |
| 发送走同一条链 | `ask(text)` 写 `VoiceInbox`（`source: keyboard`），与球上说话**同一个入口** —— 宿主那侧是同一条投递；**host 没起来时说一句"先排着"**（`ball_ask_no_host`），因为"排上了"与"送出去了"对主人是两回事 |
| 发出去了立刻关 | 服务那一侧 `boxListener.onSend`：`ask` 成功就 `closeChannel()`（不再等一个延时）；**写不进去就把框留着**，那一句还要在里面改 |
| 回复也传此通道 | 宿主 `turn/end` → `overlay op=reply`（带 `session`，那一场发来的）→ `deliverReply`：**框没开着就先张出来**（`openChannel(focus = false)`，不抢焦点、不弹键盘）再画进 `BoxView.appendReply()`；回复区上限 `BallBox.REPLY_LINES = 5`（**2026-10-06 主人追加两行：3 → 5**），到顶之后里面自己滚，滚动会给 20 s 那一笔账续期 |
| **回复框在屏上时输入投给谁**（2026-10-06 那条例外） | 框在屏上而且里面真有回复时，键盘（`ask`）与点球/唤醒词开的语音（`WakeWordService.openForOneSentence` 取一次 `OverlayState.replyTarget()`）都在队列行上带 `to: session-…`，宿主那侧把它**排在时间那笔账前面**。**目标优先取"这块框上一次投过的那一场"（`inputSession`，2026-10-09 加），没有才退回"最新那条回复是谁推来的"（`replySession`）**；`ask` 记下实际用的 `to` 当下一跳的根据。目标会话已经不在、或者不是根会话时，按"没点名"处理，落回原来那条 10 分钟规则 |
| 框在屏上时点球一下直接开口 | 平常那一档是"先召出、再点一下才说话"（`BallMinutes.summonIsFresh`），框在屏上且有回复时那一下**当场开语音**（纯函数 `BallTouch.opensVoiceNow`，判据在 `BallTest`）；开的不是"常驻"，只是一句话的窗口 |
| 开语音时框留着 | `OverlayService.speakNow()` → `parkChannel()`：窗留着（回复内容与"这一场是谁"都在它身上），只把输入框的焦点与键盘收掉，并给 20 s 那一笔账续期 |
| 提示（不是回答） | 宿主 `overlay op=note` → `deliverNote` → `BoxView.appendNote()`（同一块只读区，前面一个 `⚠`）：目前唯一一条来源是**投不出去的那句话**，见下一节 |
| 只显示回答 | 框里**不回显**主人发出去的那句（主人 2026-10-06 的口径："只显示 agent 的回复"）；回复与输入框同一套字号与颜色（都是 14 sp 正文色），分隔线分得开它们 |

框与球是**两块窗**（球不获焦、框获焦要收输入法），所以 `expand`（面板 A）与 `channel`（这块框）
互斥：开一块会把另一块摘下去 —— 两块可获焦的窗同时开着会抢输入法。

### 状态：三个字，三种颜色

球上画的是当前状态，空闲时画 **Luwi 自己那个标记**（`drawable/ic_launcher_foreground.xml` ——
一圈水花里一只鲸尾，与自适应图标的前景、单色层是同一份矢量，由 `tools/brand/luwi-mark.png` 描出来；
在球上是染白的同一份形状，不是另一张近似图）。**球上那一份比图标上大**：标记在画布里只占 0.46，
照抄进这颗球只剩一小圈，所以 `BallView` 里承载它的那块 view 比球体本身还大（`GLYPH_INK_RATIO`
= 0.65 个球体直径，多出来的透明边由球那圈圆裁掉）。图标与状态词互斥：有状态就说三个字，闲着才画它。

| 状态词 | 什么时候 | 描边与字色 |
|---|---|---|
| 正在听 | 识别链在跑（`VoiceState.capturing`；它盖住"命中/点球买来的那一句"与"视频模式常驻"两档）。**有一轮在跑时它让位给「正在想」**（2026-10-09） | 青绿 |
| 正在想 | 宿主推来的 `phase=thinking`（`turn/start` → `turn/end`），且 host 在跑。**它压过下面那两档**，而**这一档双击球 = 打断**（见「手势与菜单」） | **按会话固定的那一色**（`BallPhaseFile` 的五色轮转：琥珀 / 珊瑚 / 天蓝 / 粉紫 / 黄绿） |
| 正在念 | `VoiceState.speaking`（TTS 在念）。**有一轮在跑时让位给「正在想」**；但压过「正在听」 | 淡紫 |

**描边与那几个字用同一个色**（2026-10-09 主人："正在想的字体颜色换成对应的颜色"）：原来只有描边跟着
会话换、字恒白，两个会话同时在想时要凑近看那一圈才分得出是哪一场。现在 `BallView.show(next, animate,
ring)` 把那一个色同时喂给 `circle.setStroke` 与 `label.setTextColor`（`ring` 为 null 时退回这一档的
自带色，空闲时那两个字不可见），而**"字没换、颜色换了"那一下也要真的重画** —— 会话轮换时 `next` 还是
`BallWord.THINKING`，光比"字变没变"会把这次换色吃掉（`lastColor` 就是那第二个判据）。

优先级 **在想 > 在念 > 在听 > 失败**（2026-10-09 主人："支持互相打断，正在听时可以被正在想打断，
正在说可以打断正在听，正在说不打断正在想，不停止任务，只是优先显示并支持手动打断"）。三条关系：
麦克风开着而有一轮在跑时写「正在想」（那一档才有双击打断）；喇叭在念而麦克风也开着时写「正在念」
（念的时候半双工那道闸把麦克风整个关掉了，所以"正在念"比"正在听"更贴近事实）；一轮在跑而同时还在念
上一轮的回答时仍写「正在想」（"正在说不打断正在想"）。**「失败」让位给这三个"正在发生"的档** ——
让位不等于认过，那三个字落下之后它照样回来（`OverlayState.failedAckAt`）。

**显示与动作是两张表**：显示按上面那一条，而点球那一下仍按 **念 > 想 > 听**（`BallTouch.act` 里
`speaking` 排第一）—— 于是"球写着在想、喇叭同时在念"时，单点那一下是"别念了"，双击才是打断那一轮。

"正在想"是**宿主推来的**（`host-plugin` 的 `startBallPhase`）：一轮在跑这件事只有宿主知道，
应用这一侧没有第二条路看得出来；push 不出去时只记日志（没球的时候它就是个没人看的字段）。
宿主没在跑时那条 phase 一律不采纳 —— 否则宿主崩了，球会永远停在"正在想"。

### 动态与侧边隐藏（参考开源那一份：Petterpx/FloatingX）

那颗原型的球没在设备上露出来，所以**约定以开源实现为准**（Apache-2.0，1.5k star 的悬浮窗组件）：

- **半隐是比例，不是像素**：它叫 `FxHalfHide`，按窗口宽度算 —— 而主人 2026-10-05 点过名：
  **"半隐藏"就是球的一半在屏幕外**，所以比例取 `0.5`（不是那份 demo 的 0.3）。48 dp 的窗口推出去
  24 dp，而球体本身画在窗口中间那 45 dp 上，于是看得见的那颗球正好一半留在屏外；左贴边时窗口 x 是
  负的，右贴边时 x 超出右边界 —— 两个数都能用 `dumpsys window` 量出来
- **吸附取"剩余距离最近"的那条边**（`nearestEdge`），不是"球心过了中线就换边"
- **拖动过程中允许暂时越界，松手回弹**（`rebound`）：手上能把它推到半隐的位置，松手才收回边上
- **停靠即收边**（`adsorb(halfHide)`）：松手 → 吸附 → 半隐，一条 200 ms 的减速动画（与那套内置
  动画的缺省时长同一个数）；有人碰它、或者它有状态要说时立刻滑回来
- **闲置也收边**（vivo 那套的系统设置里叫 `floating_ball_idle_to_edge`）：最后一次活动之后
  **5 s**（`BallMinutes.PEEK_IDLE_MS`，主人 2026-10-05："4s 改为 5s，其它不变"）收半隐，给主人留一点
  时间看清它刚说了什么。半隐时透明度 0.5（那套的菜单档是 0.29，这里留亮一些好认）
- **按下缩到 0.94、拖动放到 1.06**（各 120 ms）：按住要有回应，拖起来要像"拿起来了"。**放大作用在球体
  那一层上**（窗口中间那 45 dp），所以放大之后仍在 48 dp 的窗口里 —— 球画满窗口的话，放大那一下四边
  会超出窗口被裁掉一圈（主人 2026-10-05 报过的就是这个）

### 位置与键盘

存的是**「贴哪边 + y」**，不是 x：换分辨率或转屏之后 x 要按新宽度重算（`BallGeometry.xForEdge`），
边与高度才是不变的意图。默认贴右、纵向约屏幕 2/3（D16 的"中下"）。

键盘那点高度只有**输入条**拿得到（它是唯一可获焦的那一块）：`WindowInsetsCompat.Type.ime()` 一到，
输入条整体抬到键盘上沿，球用同一个 inset 做 y 钳制。**拿不到 inset（上报 0）时两边都不动** ——
猜一个高度只会让球跳到半空中。

**收起之后那一拍要当心**（真机上抓到的一处）：输入条被摘下来之后还会来一次收尾的 IME 回调，那时它
报的还是"键盘占着 891 px"，于是球被按在键盘上沿 —— 实测比主人放的位置高了 441 px。所以两条一起
做：**摘下来的条不再认 inset**（`isAttachedToWindow` 为假就直接返回），以及收起之后清掉那个数并在
400 ms（`IME_SETTLE_MS`）后再摆一次球。

### 收边那六条闸与 2026-10-06 的几条修正

主人 2026-10-06 一次报上来四条，三条落在"球该不该收边"这一件事上，一条落在语音链上。收边的判据现在
**只有一处**：`BallRest.wait`（`overlay/BallMinutes.kt` 里那个纯函数），它吃八个读数、回"收不收"与
**为什么**，而 `refresh()` 那 400 ms 一拍只负责喂它、按它动手。六条闸按判定的先后是：

| 闸 | 什么时候算 | 那一拍报的原因 |
| :-- | :-- | :-- |
| 已经在半隐那一档 | `peeked` | `asleep` |
| 手指正按着 / 有动画在跑 | `ballDragging` 或 `snap.isRunning` | `held` |
| 菜单开着 | `menuView != null` | `menu` |
| 语音链在跑 | `VoiceState.capturing` | `listening` |
| 键盘在用 | 框在窗口上, 且（输入框有焦点 或 `imeBottom > 0`） | `keyboard` |
| 输入通道开着 | `boxOnScreen`（框真的挂在窗口上） | `channel` |

最后那一行是 2026-10-06 加上的：回答到了框会自己弹出来，而那时它**不抢焦点**（键盘不弹），所以
"键盘在用"那条不成立 —— 少了它，球会在回答出现的同时半隐溜走，而框是跟着球摆的。
**那一行留着的代价是同一天补上的**：框开着球就不收边，而框要**框外双击**才关 —— 于是回复到了之后
球可能一直露着。处置是**框自己也按空闲收**（`BOX_IDLE_MS` = 20 s，见上面那张表），框一收球那一笔账
从零起算，5 s 后收边。**不动 `channel` 那道闸**：框跟着球摆这一条没变，变的是"框不会永远留着"。

五个数（`ballWait` / `keyboard` / `idleMs` / `peeked` / `phase`）都进 `overlay op=state`，一行一句进
`files/ball-idle.txt` —— 而那台模拟器把自己的 logcat 滤掉了，所以"为什么没收边"只能靠这两处对账。
2026-10-06 起同一处还报 `boxIdleMs`（框闲置多久）与 `interrupts`（双击打断记了几笔）。

**2026-10-06 的第五条修正（"半隐藏又失效了"）**：空闲那一笔账的**重置判据必须是边沿**。原来那两行是

```kotlin
if (word != null || capturing) { if (prevWord != word) reset("state change") }
else { if (prevWord != null) reset("voice off") }
```

而 `prevWord` 只在"字换了"那一下赋值 —— 它一旦非空（出现过任何状态词：正在听 / 正在想 / 正在念）就
**再也不落**，于是每一拍（400 ms）都进 `voice off` 那一支把 `lastActiveAt` 推到当下，`idleDue` 永远
为假：球几乎从不半隐。真机上量到的指纹（`files/ball-idle.txt`，13.7 h / 20116 行）：

| 读数 | 值 |
| :-- | :-- |
| `voice off` ↔ `waiting` 互相接替 | 8052 / 8002 次（两行永远在换） |
| 全程 `peeking` / `asleep` | 14 / 13 次 |
| "该收却没条件收"的连续拍 | 40 段共 16240 拍（≈1.8 h），最长一段 4680 拍（1872 s） |

现在这两处都判**上一拍**那个字（`BallIdle.reset(next, capturing, previous)`，`previous` 每拍都落），
于是"字刚换"与"字刚落下"各只记一次账 —— `BallTest` 里那条"字落下之后的二十拍只记一次账"就是它的钉子。
`docs` 里那张时长表的"5 s 收边"从来没变，变的是**那 5 s 能不能攒起来**。

同一批的另外四条修正分别是：

1. **键盘输入不属于空闲**（主人原话）。原来打字只改 `EditText` 的文本，一个活动回调都不走，于是 5 s
   一到球就自己收起来，而框还开着。现在 `BoxView` 每一帧文本变化都报一次 `onTyping()`（也算一次活动），
   而**键盘这一档本身**由 `refresh()` 按"开始 / 结束"各记一次账 —— 打字期间不收，框一收才重新起算 5 s
2. **框开着时点球也认**。原来 `BallTouch.act` 的第一档是 `channelOpen -> NOTHING`，于是"键盘开着时点
   球打开语音"有概率什么都不发生（有概率 = 框还在的时候）。那一档拿掉了：收着点一下仍只召出、全露点
   一下进语音；"框外那一下双击"那本账照旧在按球时清掉，所以框该不该收还是由它管
3. **位置自己认账**。`unpeek()` 原来第一句是 `if (!peeked) return`，而 `moveX()` 每次都要
   `snap?.cancel()` —— 一条被掐掉的动画会留下"意图翻了而位置还在半路"这种谁也不管的状态，表现就是
   "点了说话再点一次之后球再也不收边"。现在 `unpeek()` 判的是窗**现在**在不在停靠位，并且每 400 ms
   有一次 `settleBall()` 对账（没有动画在跑时不一致就摆回去，并记一行）
4. **语音链不再把进程带走**（那条是主人看到的"整个应用重启"）。见
   `docs/wake-voice-states.md` 那一节：采集那个消费者现在是常驻的，而"这一句话的窗口"由 `vad` 那一个
   引用说 —— 关窗口时**先摘引用、再 flush 与 release**，`SpeechSegmenter.close()` 也做成幂等

### 投递卡住那一课（2026-10-06 真机）

主人报的是"键盘输入无法正常对话"：从浮标那块框里发出去的句子**落在队列里，但一个字都没进会话**。
现场数（vivo V2417A）——`files/dsh-home/voice/inbox.jsonl` 里 29 行，`inbox.cursor` 停在 `17` 且
mtime 停在 00:02，而没投出去的第一行恰好是一句**唤醒词句**（`{"text":"天气如何？","wake":true}`）；
那之后 11 句键盘"你好"与 1 句语音全排在它后面，`dsh-ball` 那个会话日志里一条 `user/message` 都没有。

根因是**一处挪动代码时漏改的判据**：`voiceTargetSession` 把 `fresh` 收进了自己（回一张
`{ sessionId: null, … }` 的记账卡，那张卡要顺带说清"为什么开新对话"），而 `voiceDeliver` 那一行还是
`target === null ? create() : target.sessionId` —— 于是唤醒词那一句拿到 `sessionId = null`，下一步
`controller.resolveAgent(null)` 必然失败。失败本身只是一句话的事，真正的病在这里：队列的规矩是
**投成功才前移游标**，所以那一句永远投不出去，而它后面**每一句都跟着卡死**；再加上这台机器
`logcat` 一个字都读不出来（`logcat -d -t 20 | wc -l` = 0），界面上于是没有任何痕迹。

三条加固（`host-plugin/index.mjs`）：

- **`voiceTargetId`**：两种"没有"（列表为空回 `null` / 唤醒词那张卡上的 `sessionId: null`）收成同一个
  `null`，"该新建"只由它回答 —— `tools/check-voice-inbox.mjs` 量它
- **一次投递 20 s 上限**（`withTimeout`）：下游某一处 `await` 永不落定也不再一直占着队列的 `running` 闸
- **同一行最多试 3 次，试满就跳过并前移游标**（`voiceAfterFailure`）：跳过不等于静默 —— 记进
  `lw_voice op=inbox`（"跳过 N 句，最近一句为什么"），并且经 `overlay op=note` 往浮标那块框推一条
  `⚠` 提示

判据：从框里发一句 → `inbox.cursor` 前移、会话日志里出现 `user/message`、回复自动弹框；投不出去时
框里那条 `⚠` 与 `lw_voice op=inbox` 的跳过计数必须都答得出来。

### 浮标通道的专用工作区（2026-10-06 主人点名）

**浮标开出来的对话都落在工作区根下的 `dsh-ball/`**（`host-plugin` 的 `BALL_WORKSPACE_NAME`
与 `ensureBallWorkspace`）：宿主进程的 cwd 与 `HOME` 都是工作区根（见 `host/DshHost.spawn`），所以
那个目录就是"工作区里一个固定的子目录"，主人的文件管理器照样看得见 —— **它是那几场对话的工作目录**
（模型在里面读写文件就落在那里），不是会话记录的存放处。

- **"浮标的对话"= 那个工作区里的会话**：唤醒词那一句开一场新的、其余接在当前那一场上，两种都由
  [ensureBallWorkspace] 定下 cwd；主人报的"投递没有进 dsh-ball 工作区"就是上一节那次收窄修掉的
- **会话记录本身在 `$DSH_HOME` 里**（`dsh-home/sessions/<工作区编码>/session-…/session.v4.jsonl.zstd`）
  —— 那是 dsh 自己的布局，所以 `dsh-ball/` 目录里**一条消息都看不到**是正常的，看对话要去会话界面：
  **双击回复框**会直接落到那一场（见「回应用那一跳」）
- **复用一个已经在跑的会话时不改它的目录** —— 一个会话的 `cwd` 是它自己的事，中途换掉就是
  `ApiSessionCwdConflict`
- 目录建不出来时退回工作区根（`controller.create({})`），**对话照旧能开**，只记一行日志：一句话
  因为目录权限没落地，比"整条投递失败"糟得多
- 想换名字就改 `BALL_WORKSPACE_NAME` 一处；它是**目录名**，英文（`dsh-ball`）是为了避开少数工具链
  的中文路径编码坑
